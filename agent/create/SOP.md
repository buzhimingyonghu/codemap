# 构建 map 的流程

把一个业务的代码画成一套可以逐层点进去的地图。最外层讲清楚这个业务是做什么的、用户的一次操作会经过哪些环节，不懂代码的人（产品、测试）也能看懂；往下一层层拆，最后落到函数和函数里的代码块。

整个过程由你（主 agent）带着用户做。理解业务、归纳模块靠你读代码和资料；有没有漏，用代码事实清单逐条核对；业务上怎么理解，在拿不准的地方和用户讨论后再定。

```
A 准备 → B 理解业务 → C 讲清楚，讨论拿不准的点 → D 写 L0 → E 按模块拆分（并行）→ F 逐层往下
```

写 yaml 一律参照同目录的模板：`node-template.yaml`（节点和地图）、`link-template.yaml`（连线上的数据）、`requirement-template.yaml`（需求变更集）。动手前用 read_knowledge 读一遍，字段含义以模板注释为准。

---

## A 准备：分析哪些资料

用户在 Codemap 里新建地图时，会选好：

- **仓库**：一个或多个本地仓库目录
- **知识库**：文档文件、文件夹、wiki 链接，也可能直接在对话里口述
- 可选：业务名称、关注重点（比如“重点看调度”“用来排障”）

只分析用户选的这些，不用再问。用户给的原始资料，在写 L0 时作为根节点的 `kb` 挂上。

如果用户什么都没给（比如通过别的入口调用这份流程）：先按业务名称在打开的文件夹里搜候选仓库和文档，列出来和用户确认，确认后再开始。不要在资料没对齐时就开始画。

## B 理解业务：只读，先不写文件

目标是用产品的视角说清楚这个业务。拿 demo 的商城举例：商城是给用户买东西的；用户的一次购物会经过下单、锁库存、支付、通知这些环节；背后是订单服务、库存服务、支付服务、通知服务，加上 MySQL、Redis、MQ 这些存储。

### B1 读知识库

先读用户给的文档，搞清：这个业务是做什么的、给谁用、有哪些用户能做的操作、有哪些专有名词。文档和代码对不上时，以代码为准，并把出入记下来。

### B2 摸清每个仓库

不要从头读代码。先列出代码里的事实：

- **入口**：HTTP 路由、gRPC 服务注册、etcd / MQ 监听、定时器、`go` 起的常驻协程、`main`
- **对外调用**：调了哪些别的服务、云 API
- **读写**：Redis、MySQL、etcd、对象存储、本地盘，各读写了什么 key / 表
- **核心对象的状态**：比如任务的 status 有哪些值，在哪里被改

工具：list_files 看目录结构，search_code 搜注册和监听的写法（Go 里常见的有 `RegisterXxxServer`、`.POST(`/`.GET(`、`.Watch(`、`NewTicker`、`go xxx(`），read_file 看入口附近的代码。

然后给每个仓库写一句话：它负责什么、被谁调、调谁。

### B3 从产品视角归纳

归纳出下面几样，这是 L0 的原料：

1. **业务定位**：一句话，做什么、给谁用。
2. **用户操作**：用户（或外部系统）会触发的事，比如下单、支付、取消、退款；后台自己跑的也算，比如“定时对账”。每个操作就是 L0 上的一条流程。
3. **业务模块**：用产品概念命名的环节，比如订单、库存、支付、通知。一个模块可以对应多个仓库，一个仓库也可以被拆到多个模块里，按“做的是哪件事”分，不按代码目录分。一般 3～8 个。
4. **模块和仓库、入口的对照**：每个模块由哪些仓库的哪些入口实现。
5. **每个操作依次经过哪些模块**，模块之间交接了什么。
6. **外部参与方和存储**：用户、调用方、第三方系统、数据库、缓存、消息队列。

划分模块时，按可靠程度依次参考：核心对象的状态怎么流转；谁触发谁（入口和调用关系）；数据从哪来、到哪去；文档、注释、日志、监控指标里用的叫法。

### B4 查漏

B2 列出的每个入口，都要能归到某个模块、出现在某个操作里。归不进去的，要么是漏了一个模块或操作，要么确实不属于这个业务（公共组件、运维接口、废弃代码），要能说出理由。反过来，每个模块至少对应一个入口；对应不到代码的模块（比如用户、第三方），标明它是外部的。

## C 讲清楚，讨论拿不准的点

先讲清楚，再讨论；不要把一张清单甩给用户逐项确认。

### C1 讲清楚

用写节点说明文档的方式（见 `node-doc-template.md`），在对话里把整个业务讲一遍：

- 这个业务是做什么的，为什么需要它
- 用户的一次操作（挑最主要的一两个）会经过哪些环节，每个环节起什么作用
- 有哪些模块，各自负责什么
- 背后用到哪些存储和外部系统

写给不看代码的人看：用业务的话，服务名、函数名最多放在括号里。

### C2 只拿出真正拿不准的点

有把握的不用问。拿不准的，每个点写清楚：

- 看到了什么（代码位置、文档原话）
- 有哪几种理解
- 推荐哪一种，为什么

常见的拿不准：一个仓库同时服务好几个业务，要不要算进来；两个环节该合成一个模块还是分开；某个入口是给用户用的还是给运维用的；文档和代码说法不一致。

### C3 和用户一起定

用户可能追问、纠正，也可能说“按推荐来”。讨论清楚后，停在 review_gate（阶段：业务理解），等用户确认再写 L0。

## D 写 L0：业务全景

L0 是一张给产品、测试看的图：一个业务是怎么运作的。

### 节点

- **用户和外部调用方**：`kind: component`，放左边（`dock: left`）
- **业务模块**：`kind: component`，`name` 用产品概念（“订单服务”“库存服务”），`brief` 写对应的服务名或仓库名，`desc` 一两句话说它做什么
- **外部系统**：第三方支付、云 API 等，`kind: component`，放右边或上边
- **存储和中间件**：`kind: resource`，放下边（`dock: bottom`）；节点库里已经有的（比如 `middleware/redis`）用 `{ ref, path }` 引用，不重复定义

### 连线

- 模块之间交接了什么，`name` 用业务的话写：“锁库存”“通知任务变了”“回报进度”
- `kind`：同步调用 `call`，异步通知或投递 `send`，返回 `return`
- 跨服务的线写 `via`，指向 `links.yaml` 里的链路，这样线上会有流动的小球，点开能看到数据。L0 的链路可以先只写接口名和关键字段，完整字段在拆模块时补全

### 流程

每个用户操作写一条流程，要求见下面的“流程怎么写”。至少要有主流程；有明显失败分支的（比如库存不足）单独写一条；有心跳、定时对账的写一条 `kind: background` 的后台流程。

### 说明文档

根节点的 `docs/<id>.md`，按 `node-doc-template.md` 写，用 `kb: [{ title: 说明, url: docs/<id>.md }]` 挂上。用户给的资料也挂进 `kb`。

### 提交

L0 的 yaml、links.yaml、docs 用 propose_change_set 提交（用 `files` 写整个文件），按回复里的校验问题改到没有错误，停在 review_gate（阶段：L0），等用户确认后写入。

每张图按“先整理、再写、最后统一校验”来做：

1. **先整理**：动手写 yaml 之前，先在心里（或回复里）列清这张图的节点、每个节点的角色（入口 / 步骤 / 闸门 / 结束）、连线和每条流程的完整步骤，对照下面“画函数图的规则”确认没有矛盾。
2. **再写**：一次 propose_change_set 调用只写一两个文件，一次写太多回复会被截断。文件多就分几次调用，第一次得到提案 id，之后每次带上 `extend: <id>` 加进同一个提案。写的过程中回复里报的问题先不管，这张图没写完不要去修。
3. **最后统一校验和修改**：这张图的文件都写完后，看最后一次回复里的全部问题，一次性改完（一次 `extend` 调用），每条错误后面都写了怎么改。不要一条一条试着改，也不要去翻别的模块找写法。

一个提案只放一张图（这张图的 yaml、links.yaml、docs）。拆节点和改父图这种必须一起生效的改动例外，放在同一个提案里。提案在你结束之前只是草稿，用户看不到按钮；你结束时它要么已经没有错误，要么剩下的你说明了原因。

## E 按模块拆分：多个子 agent 并行

L0 确认后，每个业务模块交给一个子 agent（delegate_nodes），同一时间并行几个由设置决定。

### 给子 agent 的任务包

在 instructions 里写清楚：

- 这个模块负责什么（照 L0 的说明）
- 对应的仓库、目录，以及 B2 里归到它名下的入口
- L0 上进出它的连线：子图里必须把这些线接上，外侧那端用 `{ ref, path }` 引用
- 它参与的 L0 流程：子图的流程用 `refines` 接着这些流程往下展开
- 相关的术语和用户给的资料

### 子 agent 做什么

1. 读入口附近的代码，弄清这个模块内部分几块
2. 写这个模块的说明文档 `<模块文件夹>/docs/<id>.md`（按 `node-doc-template.md`），并挂到节点的 `kb` 上；和 yaml 放在同一个 propose_change_set 里提交
3. 写模块的 yaml：内部的服务、组件或入口函数；每个函数节点写 `fn.repo` + `fn.code`
4. 写 `links.yaml`：每个对外接口一条链路，字段从代码里的结构体照抄，写上 `repo` + `code`
5. 自查：propose_change_set 的回复里没有错误；L0 进出它的线都接上了；归到它名下的入口都画了；说明文档讲的和图上画的一致
6. 交回报告：画了什么，哪些地方不确定，哪些需要别的模块配合

### 分工规则

- 子 agent 只写自己模块的文件夹
- 存储、公共组件这类多个模块共用的东西，由主 agent 放在节点库的公共位置
- 发现 L0 或别的模块要改，写在报告里，由主 agent 处理

### 主 agent 汇总

看所有报告，检查：模块之间的接口两边是否一致（一边画了调用，另一边要画被调用）；流程能否从一个模块接到下一个模块；有没有两个模块画了同一段代码，或者有入口没人画。需要改的自己改或再派一次。最后停在 review_gate（阶段：模块拆分），等用户审。

## F 逐层往下：直到函数和代码块

模块拆完后，挑节点继续往下拆，做法和 E 一样，复杂的节点同样交给子 agent：读代码 → 写这个节点的说明文档 → 画图 → 自查，文档和图一起提交。

### 每层画什么

| 层 | 节点是什么 | 按什么排 |
| - | - | - |
| L0 | 业务模块、用户、外部系统、存储 | 一次操作经过的先后 |
| L1 | 模块里的服务、组件 | 请求和数据在它们之间的流向 |
| L2 | 服务里的职责块、入口函数 | 入口 → 处理 → 输出 |
| L3 及以下 | 函数里的步骤、判断、循环 | 代码执行的顺序 |

### 拆不拆

- **该拆**：一个节点管的代码里有好几个业务分支（不算 `if err != nil`、参数校验、补默认值），或者直接读写好几类存储，一张图讲不清
- **不拆**：内部就是顺序的几步，节点上的 `desc` 已经说清楚了
- **到底**：拆到函数里的代码块（`fn.code` 只写行号）就停
- 用户在地图上选中某个节点让你拆，就拆这个

先拆核心路径和用户关注的部分。每拆完一批，停在 review_gate。

一层只往下画一层：模块的子图先画成“模块里的几块”（`kind: component`，每块写清职责和对应的代码入口），不要在这一层直接画成函数；函数和函数间的执行顺序留到再下一层。只有一个模块本身就是一两个函数时，才直接画函数图。

### 每层都要满足

- **接得上**：父图里进出这个节点的线，子图里要有对应的入口和出口（校验规则 edge-mutual、edge-lift）
- **流程连续**：子图的流程 `refines` 父图的流程，进出这个节点的步骤顺序一致（flow-refines）
- **粒度一致**：同一张图里的节点抽象程度差不多，不要“调度系统”旁边放一个“解析 JSON”
- **父节点的分支都有着落**：父函数里的每个业务分支，都落在某个子节点上

## 每张图怎么写

### 模板特性

| 特性 | 用在哪 | 怎么用 |
| - | - | - |
| `name` / `brief` / `desc` | 每个节点 | name 中文说清楚做什么（“锁库存”）；brief 写服务名、函数名或关键参数；desc 一两句话 |
| `kb` | 每个有子图的节点 | 挂 `docs/<id>.md`，外部文档也挂上 |
| `lanes` + `dock` | 每张图 | 调用方 left，依赖服务 top，存储 bottom，下游 right，中间按处理顺序排 |
| `{ ref, path }` | 跨图的节点 | 别的模块、共用的存储用引用，不重复定义 |
| `edges.kind` | 每条线 | next 下一步，call 调用，send 投递或通知，return 返回 |
| `edges.mode: go` | 起协程的线 | 调用方不等结果 |
| `edges.via` | 跨服务、读写存储的线 | 指向链路，线上才有小球和数据卡片 |
| `links.yaml` | 有接口的节点 | 一个接口一条；http / grpc / tcp / mq / redis / sql / func；字段照代码写全，带 repo + code |
| `when` / `error` / `swallow` | 分支 | 判断节点（写了 `fn.check`）至少两个出口，每条写条件；错误分支标 error |
| `fn.trigger` / `fn.serves` | 入口函数 | 怎么被调起来，实现了哪条链路 |
| `fn.type: listen` / `timer` + `every` | 监听、定时 | 图上看得出它是常驻监听还是定时跑 |
| `fn.outcome` / `terminal` | 结束节点 | 成功和失败的出口都画出来 |
| `fn.code` + `fn.repo` | 函数节点 | 必须有，精确到行；函数内部的代码块只写行号 |
| `fn.io` / `reads` / `writes` / `guards` | 产出结构体的函数 | 回放时右侧结构体卡片逐个字段点亮 |
| `flows` | 每张图 | 见下面 |
| `kind: background` + `period` | 心跳、定时巡检 | 单独一条后台流程 |
| `issues` | 看代码时发现的疑点 | 这次不修、后面要查的，写清问题和代码位置 |
| `review: { status: draft }` | 每个节点 | 新画的都是 draft，开发核对后改 reviewed |

### 流程怎么写

每张图至少一条流程。流程是给人看的：只看步骤列表，不看代码的人也要能读懂这件事是怎么完成的。

- **一个具体的场景**：`scenario.desc` 写成一件具体的事，“用户 9527 买 sku 1001 × 2”，而不是“用户下单”；结构体卡片的示例值写在 `scenario.values`
- **每步一句话**：`title` 说这一步在做什么，用业务的话（“锁库存”“写进度和断点”），不要只写函数名
- **说出结果**：关键步骤写 `result`，这一步产生了什么、做了什么决定（“库存 120 → 118”“切成 3 个子任务”）
- **数据看得见**：跨服务的步骤写 `data`（传的是哪份数据）和 `sample`（示例载荷）
- **讲得通**：步骤之间有因果，读下来是一个完整的过程，不跳步；分支走了哪条，用 result 说明为什么
- **接得上**：子图的流程用 `refines` 指向父图的流程
- **能播放**：每一步 from → to 都在图里的连线上

除了主流程，再按需要加：失败或异常怎么走（库存不足、下载失败、节点挂掉），后台流程（心跳、定时对账）。

### 说明文档

每个有子图的节点都有说明文档，放在这个节点自己的文件夹里：`<节点文件夹>/docs/<id>.md`，按 `node-doc-template.md` 写，挂在节点的 `kb` 上（`kb: [{ title: 说明, url: docs/<id>.md }]`）。

文档跟着节点走：

- **新拆一个节点**：画图的同时写好它的说明文档，一起提交
- **改一个节点**（拆分、合并、加分支、改流程、改名）：先 read_file 读现有文档，把改动涉及的段落改掉，和 yaml 一起提交；不要只改图不改文档
- **改动影响到父节点**（父图上的连线、流程、对它的描述变了）：父节点的文档也要跟着改
- 文档里“怎么做的”要按改完后的主流程重新讲一遍，不要在末尾追加“新增了 xx”这类改动记录

## 画函数图（执行图）的规则

图里有 `kind: function` 的节点，就按执行图校验。每个函数的角色由 `fn` 字段决定，规则如下，提交前对一遍：

| 角色 | 怎么写 | 规则 |
| - | - | - |
| 入口 | `fn.trigger` 或 `fn.serves` | 图内不能有线连进来；外面的调用方（etcd、调用方服务）连进来可以。被同图别的函数启动（`go xxx()`）的函数不是入口，不写 trigger |
| 步骤 | 都不写 | 要有往下走的线，或者调用外部节点；写了 `type: listen` / `timer` 的常驻循环可以没有 |
| 闸门 | `fn.check` | 至少两个出口，每条写 `when` |
| 结束 | `fn.outcome` | 图内不能再往下连；要有一条连到外部的线（比如调 worker、回给调用方），或者写 `fn.terminal: true` |

常见写法：

- 启动函数起了好几个协程：只有启动函数写 `trigger`，连到各协程的线写 `kind: call, mode: go`，各协程函数不写 trigger。
- 一个动作做完还要交给图内别的函数（比如停 worker 后投递清理事件）：它就不是结束，不写 `outcome`。
- 分支条件写在连线的 `when` 上，流程步骤里不写 `when`，走了哪条分支用 `result` 说明。
- `issues` 的 `code`：函数节点的仓库取 `fn.repo`，组件节点取组件自己的 `repo`。

有错误的提案不能写入。看回复里的错误逐条改，用 `extend` 在同一个提案上改到没有错误为止，再停下来交给用户。

## 每次提交前自查

- propose_change_set 的回复里没有错误（error）；警告能修的修掉，修不了的在 `ignore` 里写原因
- 每张图至少一条流程，流程能从头播放到尾
- 每个有子图的节点挂了说明文档
- 这次新建或改动的节点，说明文档都写了或更新了，内容和图一致
- 函数节点都有 `fn.code` + `fn.repo`，链路的数据都有 `repo` + `code`
- 这张图负责的入口都画了，读写的存储都连了线
- 名字是给人看的：中文说清楚做什么，函数名放 brief

## 审核点

在这些地方停下（review_gate），把这一步做了什么、需要用户看什么写清楚：

1. 业务理解讲清楚、拿不准的点讨论完之后
2. L0 画完之后
3. 模块拆分汇总之后
4. 之后每拆完一批节点

用户通过就继续；用户提了意见，按意见改完再停一次。

停下来给用户看的，只有架构和逻辑：怎么拆的、每块做什么、流程讲得对不对、哪里拿不准。校验器报的问题由你在停下之前全部改完，不要拿给用户看，也不要问用户怎么改；提案还有错误时 review_gate 会被拒绝。
