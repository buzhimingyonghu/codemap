# 领域术语

建图和改图时，名称以这里的术语为准，不要临时换同义词。

- **全局笔记**：`agent/domain/*.md`。随应用发行，所有模式都会装入系统提示词。只放跨项目都成立的术语和约束。
- **项目笔记**：节点库根目录的 `<library>/domain.md`。它会自动装入系统提示词，只对这个节点库有效；与全局笔记冲突时，以项目笔记为准。

项目笔记建议只写这四节，没有内容的节删掉。不要写密码、token、账号或下载链接。

1. **核心术语对照**：业务叫法 → 代码 / 配置里的名字。节点 `name` 用左边，`brief` 用右边。
2. **服务职责边界**：每个进程或独立子系统负责什么、不负责什么。`service` 视角按这里切 `component`，避免把多个服务揉进一个产品名词。
3. **核心状态枚举**：业务对象的状态值、谁改它、哪些值是终态。`troubleshoot` 视角按这里画超时、重试、回滚和对账。
4. **忽略目录说明**：生成代码、供应商、运维探针、废弃入口为什么不画；与 `.codemapignore` 一致。排除原因写在这里，建图时不要静默漏掉。

四节都用短列表。术语对照写“业务叫法 → `代码名`”；职责边界写进程名和不负责的邻居；状态枚举写取值、改它的服务、是否终态。

写节点名、`desc`、流程 `title` 和说明文档前先查这份笔记。笔记没有、代码又对不上文档时，以代码为准，并在回复里标出差异。

不要擅自改笔记，除非用户要求补充术语。补充时只追加已经在代码或文档里出现过的叫法，不发明新同义词。

建图（`service` / `business` / `troubleshoot`）和局部改图都先读项目笔记，再读全局笔记。笔记没覆盖的新名词，节点上先用代码里的名字，并在回复里标“笔记未收录”。

同一业务对象只用笔记里的一个中文名。状态值保持代码原样，不翻译成近义词。
